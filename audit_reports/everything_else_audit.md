## .claude/hooks/session-start.sh

### Live evidence that the staged-sequence invariant this orchestrator encodes is not actually being enforced

The whole point of this hook's `if`/`elif` chain (L47-118) is to run the enrichment drivers in a strict sequence — deep (`run_deep_forever.sh`) → OTC (`run_otc_deep.sh`) → rest (`run_rest_deep.sh`) → Lynch (`run_lynch_enrich.sh`) → standard ticker_yf/chart — gated on each stage's sentinel file, because (per every driver's own header comment, and this hook's inline comments at L41-46/61-63/75-79/91-93) **only one enricher may hit Yahoo Finance at a time** or they starve each other on the shared-IP rate limit ("the failure that repeatedly killed OTC before the sole-hitter invariant was enforced," per `run_rest_deep.sh`'s own comment). `run_lynch_enrich.sh`'s branch (L85-90) requires `.deep_rendered` **and** `.rest_rendered` to both exist before it is ever launched by this hook.

At audit time: `run_lynch_enrich.sh` **is actively running** (confirmed via `ps aux`: pid 1701 `bash run_lynch_enrich.sh`, pid 2446 `python3 lynch_reward_enrich.py --rate 2.5 --limit 800`), yet **none of `.deep_rendered`, `.otc_rendered`, or `.rest_rendered` exist anywhere on disk** (all four confirmed absent via `ls`). Per this hook's own gating logic, branch 4 (Lynch) could not have fired this way — its condition requires `.deep_rendered` and `.rest_rendered` to be present, and they are not. So either (a) this specific launch of `run_lynch_enrich.sh` bypassed the hook entirely (started out-of-band, manually or by an earlier ad hoc session), or (b) there is a sequencing defect somewhere in how this chain gets evaluated across repeated session starts that let it fire early. I cannot fully distinguish (a) from (b) from inside this container, but either way the **practical, currently-true fact** is: the staged ordering this hook is supposed to guarantee is not holding right now, and — critically — **no driver script defends this invariant itself**: `run_lynch_enrich.sh` (read in full above) never checks `.rest_rendered`/`.deep_rendered` before proceeding; it trusts entirely that whatever launched it already verified the precondition. The "SOLE Yahoo hitter" safety property this whole multi-driver design depends on is therefore enforced at exactly one point (this hook's gating logic) with zero defense-in-depth in any of the drivers themselves — a single point of failure for an invariant the repo's own comments say has already caused real damage once ("the failure that repeatedly killed OTC"). (In this specific instance the risk was not realized — no other Yahoo-hitting process was concurrently running per the same `ps aux` snapshot — but the gating that is supposed to *guarantee* that had, in fact, already been bypassed.)

### Consequence of the above — a fresh hook firing right now would double-launch `run_deep_forever.sh` alongside the already-running `run_lynch_enrich.sh`

Given the current on-disk state (no `.deep_rendered`, `.otc_rendered`, or `.rest_rendered`, and `run_deep_forever.sh` not currently running per `pgrep`), the **first** branch of this hook's chain (L47-55) would evaluate true if the hook fired again right now — it would `setsid nohup bash run_deep_forever.sh` in the background, which would immediately start hammering Yahoo via `ticker_yf_deep.py` **concurrently with the already-running `run_lynch_enrich.sh`/`lynch_reward_enrich.py`**, exactly the "three concurrent hitters starve each other" scenario every one of these drivers' comments explicitly warns against. This is a directly demonstrable consequence of finding above, not a hypothetical: the sentinel state on disk right now would cause this hook, if triggered, to violate its own core safety invariant.

### Minor
- `.otc_rendered` is checked as a precondition for launching `run_rest_deep.sh` (L69-72) but is **not** re-checked in the terminal branch that resumes the standard `ticker_yf`/`yahoo_chart_fill` enrichers (L99-100 checks only `.deep_rendered` + `.rest_rendered` + `.lynch_done`). Under the intended strictly-sequential flow this is harmless (`.otc_rendered` is transitively implied by `.rest_rendered` since branch 3 requires it to have started) — but given the confirmed finding above that stages can and do run out of sequence in this environment, an out-of-band `.rest_rendered` (e.g. manually touched, or created by a driver run directly without going through this hook) with `.otc_rendered` never actually set would let the terminal branch resume the standard enrichers while OTC deep enrichment was silently skipped, with nothing here to catch it.
- The `pip3 install` dependency-refresh step (L28-34) logs a warning but does not abort or gate the subsequent driver launches on success (`... || echo "... had errors ..."`, L33, then execution falls through unconditionally to the launch chain). If a dependency genuinely fails to install (network hiccup during session start, a real version conflict), every driver launched afterward will crash on its first Python import with no visibility from this hook (each driver's own log captures the traceback, but the hook's own stdout claims "launched ... driver (PID N)" regardless of whether that process is still alive a second later). Corroborating but inconclusive: `financedatabase` (required by `fdb_sector_hydrate.py`/`build_fdb_expansion.py`) is not importable in this container right now, and no `pip_install.log` exists on disk — consistent with either this hook never having fired in this container's history, or a silent dependency-install gap; not enough evidence here to say which.

## run_ticker_yf_forever.sh

### CRITICAL — this driver never commits or pushes anything to git; the gitignored sentinel it writes on completion can silently mask a full loss of its work

`grep -n "git " run_ticker_yf_forever.sh` returns **nothing** — unlike its two sibling drivers (`run_deep_forever.sh`, `run_lynch_enrich.sh`), which both `git add`/`commit`/`push` their progress mid-loop and again on completion, this driver's entire Phase 2 (`apply_ticker_yf.py`, `fill_asymmetry_gaps.py`, `derive_missing_columns.py`, `rebuild_scores.py`, `enrich_asymmetry_global.py`, `archetype_tags.py`, then the full 11-command workbook rebuild loop, L67-90) runs and then just writes the sentinel `.ticker_yf_rendered` (L92) — with **no commit of `asymmetry_global.csv`, `archetype_tags.csv`, or any of the rebuilt `.xlsx` workbooks**. `.ticker_yf_rendered` is itself gitignored (confirmed in `.gitignore` L32), so it exists only on local disk, never in git history. Consequence: once this driver completes in a given container, all of the (potentially hours of) re-render work it just did lives **only on that container's local disk** — if the container is reclaimed, restarted from a git clone, or its disk is otherwise not preserved, that work is gone, with no record in git that it ever happened. Worse, if the *same* container/disk persists across a restart of this script (rather than a fresh clone), the driver sees its own gitignored sentinel still present and **skips straight to exit** (L32-35) without ever re-running or re-committing — so a supervisor that assumes "sentinel present ⇒ the results are safely persisted" would be wrong on both counts (not committed, and not re-derivable without deleting the sentinel by hand). This is the same class of bug as the audit brief's "state files that can mark work done when it failed" — here the state file marks *durability* as done when the actual durable copy (git) was never written. Live corroboration: `git status --short` at audit time shows 27 modified-but-uncommitted files sitting in the working tree right now (including `asymmetry_global.csv`, `archetype_tags.csv`, several `build_*.py` scripts, and multiple `.xlsx` workbooks) — real, current, uncommitted state that a container reclamation would lose today. Recommend adding the same `commit_progress`/final-commit pattern already used in `run_deep_forever.sh` and `run_lynch_enrich.sh` to this driver.

### Same missing-render-step findings as `run_deep_forever.sh` (duplicated chain)

The Phase 2 workbook-rebuild loop here (L77-90) is a near-verbatim copy of `run_deep_forever.sh`'s render chain and inherits the identical gaps documented in that section: no `methodology_audit.py` call (even though this driver, too, runs `archetype_tags.py` immediately followed by `enrich_asymmetry_global.py` — exactly the sequence that tool's docstring says should trigger it), and no invocation anywhere of the OTC/52-week-high book variants (`top_n_by_country.py --otc-mode ...`/`--high-filter ...`, `build_country_archetype_book.py`/`build_country_archetype_inflection_book.py` with the same flags) that produced the orphaned `top_n_otc.*`, `top_n_52w_high.*`, `country_archetype_52w_high.xlsx`, `country_archetype_book_otc.xlsx`, `country_archetype_inflection_otc.xlsx` files sitting in the repo with no reproducing command anywhere. That the exact same chain — and the exact same omissions — appears copy-pasted across two independent driver scripts is itself worth flagging: a fix applied to one will not propagate to the other unless someone remembers to patch both.

## edgar_segments_extract.py

### CONFIRMED (real data) — same fact value fanned out into multiple rows when a context carries 2+ "interesting" dimensions

`extract_facts` (L93-110) loops `for axis, member in relevant_dims.items(): rows.append(...)` — when a single XBRL context is dimensioned by **more than one** axis in `INTERESTING_AXES` simultaneously (e.g. a R&D-expense fact broken out by both `srt:ProductOrServiceAxis` AND `us-gaap:StatementBusinessSegmentsAxis` on the same context), the identical dollar `value` is emitted as **one row per axis** rather than one row for the (axis, member) *tuple-set*. Verified against the live cache: scanning `edgar_segments_cache/*.json`, **113,883 of ~6.1M dimensioned facts** carry 2+ `INTERESTING_AXES` dimensions at once (e.g. `edgar_segments_cache/CIK0001828185.json`, accession `0001828185-26-000012`, concept `brns:DirectResearchAndDevelopmentExpense`, value `6,063,000` — emitted as two separate rows, one tagged `srt:ProductOrServiceAxis`/`VTP1000CeliacMember` and one tagged `us-gaap:StatementBusinessSegmentsAxis`/`ResearchAndDevelopmentOfImmunotherapiesAndVaccinesMember`). Any downstream consumer that aggregates `value` per (symbol, concept, period) without also grouping by `axis` will double-count this figure. `edgar_segments.csv` and `edgar_segments_summary.csv` carry no column flagging "this value co-occurs on N axes", so the trap is invisible to a consumer working only from the flat CSV.

### CONFIRMED (real data) — duplicate/conflicting values across accessions for the same reported period, no recency tiebreak

Because `edgar_full_harvest.py` deliberately pulls the latest **two** 10-Ks (current + prior FY, each containing its own prior-year comparative column), the same fiscal period is reported by two different accessions. `extract_facts` concatenates rows from every accession with no dedup and no "most-recent-filing-wins" resolution. Verified on Accenture (`CIK0001467373.json`): FY2024-08-31 EMEA segment revenue (`us-gaap:Revenues`) appears identically as `22,817,879,000` under both accession `0001467373-24-000278` (as its own current year) and `0001467373-25-000217` (as the prior-year comparative) — a clean duplicate. Worse, the same period's **D&A** for the same segment differs between filings: `501,749,000` (as reported in the FY2024 10-K) vs. `521,944,000` (as restated/re-presented in the FY2025 10-K's comparative column) — a real restatement, but the CSV has no `accession`-recency ordering or dedup key, so a naive groupby-and-average or groupby-and-first over `edgar_segments.csv` will nondeterministically pick either the stale or the restated figure (pandas groupby order follows first-seen-in-file, which follows `sorted(CACHE_DIR.glob("*.json"))` then dict-iteration order of `facts_by_filing` — i.e., filename-then-JSON-key order, not filing-date order), and any naive `.sum()` grouped only by (symbol, concept, period_end) double-counts the revenue.

### Inconsistent axis whitelist between the dimension filter and the concept-fallback filter

`INTERESTING_AXES` (L31-45) includes `us-gaap:SegmentAxis`, `srt:StatementGeographicalAxis`, `srt:GeographicalAxis`, `us-gaap:MajorCustomersAxis`, `us-gaap:CustomerConcentrationRiskAxis`, and `dei:LegalEntityAxis` — but the secondary "allow non-whitelisted concept" fallback (L87-91) only re-checks 4 axes: `us-gaap:StatementBusinessSegmentsAxis`, `us-gaap:StatementGeographicalAxis`, `srt:ProductOrServiceAxis`, `us-gaap:ProductOrServiceAxis`. A custom/company-specific concept (anything outside `INTERESTING_CONCEPTS`) dimensioned *only* by `us-gaap:SegmentAxis`, `srt:StatementGeographicalAxis`, `srt:GeographicalAxis`, `MajorCustomersAxis`/`CustomerConcentrationRiskAxis`, or `LegalEntityAxis` passes the first filter (dim present in `INTERESTING_AXES`) but is then silently dropped by the second filter, with no counter or log of how many facts were discarded this way. This is a silent coverage gap for company-specific revenue/margin tags reported only by geography or customer-concentration axis variants that aren't the exact 4 whitelisted strings.

### Minor
- `if value is None: continue` (L75-76) does not filter out `NaN` values — `harvest_xbrl_dimensional` in the harvester round-trips `float('nan')` through `json.dump`/`json.load` (Python's json module permits literal `NaN` by default), so facts with a legitimately-missing numeric value (`nan`, not `None`) can pass through into the CSV as blank cells rather than being excluded. Low impact since `INTERESTING_CONCEPTS` rarely produces NaN in practice, but inconsistent with the apparent intent of the None-check.
- `top_revenue_segments` in the summary output (L146-158) ranks segment members by **occurrence frequency** in the most recent 20 rows (`.value_counts().head(3)`), not by dollar magnitude — the column name implies a revenue-size ranking it doesn't actually compute. Cosmetic/naming risk for anyone consuming the summary CSV at face value.

## persist_edgar_segments.py

### Part-boundary mid-row split — verified CORRECT (not a bug)

The audit brief specifically asked to verify the line-boundary split. Traced carefully: `save()` (L38-58) splits into a new gzip part only between raw physical lines read via `for line in fh` (Python splits on `\n`), which can fall in the middle of a *logical* CSV row if that row contains an embedded newline inside a quoted field. However `restore()` (L66-78) reconstructs by concatenating each part's raw decompressed bytes back-to-back, discarding only the redundant leading header line of parts `i>0` (via an unconditional `fh.readline()` before `shutil.copyfileobj`) — it never re-parses or re-aligns on row boundaries. Because the split point is purely positional and every byte on either side of the split is preserved and reassembled in original order, the round trip is byte-exact regardless of whether the split fell mid-logical-row. **No defect** — flagging as verified-clean per the specific ask.

### Silent data loss — `restore()` never checks the part sequence is contiguous

`restore()` (L67) does `parts = sorted(glob.glob(os.path.join(PARTS_DIR, "part_*.csv.gz")))` and stitches together **whatever files are present**, with no check that `part_000..part_{N-1}` form an unbroken sequence. If any single part file is missing — not committed, dropped by a bad git operation, corrupted and manually deleted, lost to an LFS/size-limit issue — `restore()` silently reconstructs a truncated `edgar_segments.csv` (missing exactly the rows that lived in the dropped part) with **zero warning**, and the "restored N part(s), X MB" success message (L77-78) looks like a normal, correct restore. This is precisely the "state/artifact that reports success while having silently lost data" failure mode the audit is hunting for, applied to the one file this repo's own docstring says exists specifically to prevent catastrophic data loss (L3-7: "the harvest was lost once... never again"). Recommended fix: assert the sorted basenames are exactly `part_000.csv.gz, part_001.csv.gz, ..., part_{N-1}.csv.gz` with no gaps before reconstructing.

### Operational staleness observed live (not a code bug, but a real gap)

## fix_pipeline.py

### CRITICAL, CONFIRMED BY REAL DATA — currency lookup for FX conversion is keyed by bare symbol with alphabetical-file-order tiebreak, causing genuine 100x GBp/GBP-class unit errors

`fix_asymmetry_global` (L192-221) builds the currency map that drives the entire FX-to-USD conversion this way (L200-210):
```python
for f in sorted({p for g in ['*_yartseva.csv'] for p in glob.glob(g)}):
    d = pd.read_csv(f, usecols=['symbol','currency'])
    for sym, ccy in zip(d['symbol'], d['currency']):
        if isinstance(sym, str) and isinstance(ccy, str) and sym not in ccy_map:
            ccy_map[sym] = ccy   # FIRST FILE (alphabetically) WINS, unconditionally
df['currency'] = df['symbol'].map(ccy_map)
```
This ignores `src`/country entirely and, worse, ignores *which yartseva file's row actually became the `asymmetry_global.csv` row for that symbol* — it just takes whichever `*_yartseva.csv` file sorts first alphabetically among all ~100+ files in the repo that happen to contain that bare ticker string. `fx_convert`'s `SUBUNIT` table (L170-173) already documents that this exact mistake is a live danger: "Yahoo quotes some markets in 1/100 units (London pence...) ... without this it would default to fx=1.0 — a ~100x error." The lookup that feeds `SUBUNIT` is precisely the one shown above, and it has no defense against picking the *wrong* subunit/full-unit variant for a symbol whose value in `asymmetry_global.csv` actually came from a different file.

Verified with real data: scanning every `*_yartseva.csv` for symbols that carry **more than one distinct currency string** across files, **620 symbols** conflict, and the dominant failure pattern is exactly `GBp` (pence, ÷100) vs `GBP` (pounds) — e.g. `AFC.L`: `fdb_expansion_yartseva.csv` says `GBp`, `uk_yartseva.csv` says `GBP`; `UFO.L`, `AGY.L`, `AEX.L`, `BYG.L`, `FUM.L`, `HMSO.L`, `HAYD.L` show the identical pattern; `DRD.JO` shows the equivalent `ZAc`/`ZAC` (cents) vs. implicit-full-unit conflict. Whichever of the two conflicting files happens to sort alphabetically first (`fdb_expansion_yartseva.csv` before `uk_yartseva.csv`, `f` < `u`) wins the `ccy_map` entry for **every** downstream row of that symbol, regardless of which file's units the actual `asymmetry_global.csv` market_cap/revenue/ebitda/fcf figures were pulled from. Since `SUBUNIT` divides by 100 for `GBp`/`ZAc`-class currencies and does not for the full-unit form, a mismatch between the assigned currency label and the row's actual units produces a **100x** error in `market_cap_usd`/`revenue_ttm_usd`/`ebitda_ttm_usd`/`fcf_ttm_usd`/`enterprise_value_usd`/`net_cash_usd`/`ncav_usd` (L184-188) — either 100x too small (full-unit value mislabeled as pence) or 100x too large (pence value mislabeled as full pounds) — for any of these 620+ colliding symbols, silently, with no warning, baked straight into the master file every downstream USD-comparison / cross-country ranking script relies on. Given `GBP` is one of the most heavily represented currencies in this universe (the UK contributes several large yartseva files), this is not a fringe edge case.

## sedar_backlog_scraper.py

### CONFIRMED via reproduction — `BOARD_KEYWORDS` misses the single most common board-appointment press-release phrasing (plural "Directors")

`BOARD_KEYWORDS` (L48-55) is the regex used to detect "recently appointed board member" headlines — the second of the two qualitative signals this script exists to verify (per its own docstring, L8-10). Every alternative in the pattern ends the word `director` (singular, no `s?`) immediately followed by the outer `\b` word-boundary assertion. Because `\b` requires a transition between a word char and a non-word char, `director` immediately followed by a plural `s` (as in "...Board of **Directors**", by far the most common press-release phrasing) has no boundary there and the match fails. Reproduced directly against realistic headlines:
```
'XYZ Announces Appointment of Jane Doe to the Board of Directors'  -> False   (misses the classic press-release phrasing entirely)
'Company Appoints Two New Directors to the Board'                  -> False
'ABC Corp Elects Two New Directors'                                -> False
'ABC Corp Elects New Director to Board'                            -> True   (only the singular form matches)
```
This means the tool silently fails to detect exactly the recent-board-appointment signal it was built to confirm, for any headline using the (near-universal) plural "Directors." Fix: add `s?` after every `director` occurrence in the pattern (and after `board\s+member`/`chair(?:man|person)?` for symmetry).

### Silent, effectively dead error handling — SEDAR+ failures are unobservable

`fetch_sedar_recent_filings` (L134-174) wraps its own request/parse in a `try/except Exception: return []` (L158-164) that swallows every failure mode — a non-200 status, a connection error, a non-JSON response body (SEDAR+'s public search is plausibly behind bot mitigation, and the docstring's claim that it "returns JSON when called with the right Accept header" is asserted, not demonstrated in-repo) — and returns an empty list indistinguishable from "issuer genuinely has zero recent filings." The caller (`assess_ticker`, L218-222) wraps the *call* in its own `try/except Exception as e: sig.error = f"sedar: {e}"` — but since the callee never lets an exception escape (it always returns `[]` instead of raising), this outer handler is **dead code**: `sig.error` can essentially never be set via the SEDAR path, so there is no way to distinguish "SEDAR+ was checked and had nothing" from "SEDAR+ was unreachable/blocked for the entire run" anywhere in `archetype_qualitative_signals.csv`. Same silent-zero pattern applies to `fetch_yfinance_news` (L88-107): every failure branch returns `[]`, so `n_news=0` is ambiguous between "no news" and "fetch failed," and `sig.error` is never populated from that path either. For a script whose entire purpose is producing a qualitative research signal, a systemic fetch outage would silently present as "no confirming signal found" (i.e., bearish/neutral) across the whole run rather than as a visible error — and no CSV of this script's own output currently exists in the repo to spot-check (`archetype_qualitative_signals.csv` is absent), so it's unclear whether this has ever produced usable SEDAR+ data at all in this environment. Recommend: record a distinct `sedar_error`/`news_error` field for actual fetch failures (HTTP error, exception, non-200) versus a genuine empty result.

### Minor
- The `--from-archetype` merge (`asym.merge(arch, on='symbol')`, L253-255) joins purely on bare `symbol`, inheriting the repo-wide ticker-collision risk documented elsewhere in this audit (e.g. `edgar_to_yartseva.py`'s confirmed `ATS` collision) — a symbol reused across two countries in `asymmetry_global.csv`/`archetype_tags.csv` could pull the wrong name/country pairing into a target before the `src == args.from_archetype.upper()` filter is even applied, though the `src` filter does correct for the most obvious case (an exact-duplicate symbol from a different country is filtered out downstream by the `src` check, so the practical exposure here is narrower than in the EDGAR price-merge case).

## edgar_mda_parser.py

### CRITICAL, CONFIRMED BY REPRODUCTION — sentence regex truncates at any embedded decimal point, corrupting extracted dollar values by ~1,000,000x

`BACKLOG_SENTENCE_RE` (L56-61) defines a "sentence" as `[^.!?\n]{0,250}? <keyword> [^.!?\n]{0,250} [.!?]` — the character class `[^.!?\n]` excludes literal `.`, which means a **decimal point inside the dollar figure itself** (e.g. `$1,234.5 million`) is treated as the sentence terminator. Reproduced directly:
```
text = "Our total backlog grew to $1,234.5 million as of year end, driven by strong order intake in the segment."
BACKLOG_SENTENCE_RE match -> 'Our total backlog grew to $1,234.'
VALUE_RE on that snippet   -> matches "$1,234" with NO unit suffix (the "million" got severed into a second, keyword-less fragment: '5 million as of year end...')
_to_value("1,234", None)   -> 1234.0
```
So a real $1,234,500,000 backlog is recorded as a raw `$1,234` value — off by a factor of ~1,000,000 — with no error, no warning, and a plausible-looking (if tiny) row written straight into the CSV / summary output. Because financial filings routinely state large figures with one decimal place before the unit word (`$45.2 billion`, `$1,234.5 million`), this is not an edge case — it will misfire on a large fraction of real backlog disclosures that include a decimal. The second half of the original sentence (the actual `million` unit word, plus the rest of the paragraph) becomes an orphaned regex match that starts a fresh scan without the `backlog` keyword in it, so the unit information is simply lost rather than merely misattributed. Fix: exclude only sentence-ending punctuation that is *not* immediately preceded/followed by a digit (e.g. a lookaround-based sentence splitter, or pre-mask decimal points in numbers before running the sentence regex).

### Corroborating evidence from the existing `edgar_mda_readings.csv` (Boeing, CIK from a prior real run)

Row `period_end=2026-03-31, value=6.947090e+05, unit_str="$ 694,709"` records Boeing's backlog as **$694,709** (fully unscaled) from the sentence "Our backlog at March 31, 2026 was $ 694,709." — Boeing reports this table in **millions**, so the true figure is ~$694.7 **billion**, understated here by ~1,000,000x because no unit word happens to sit next to that particular sentence's number (the "$ in millions" scale is stated once in a table header the sentence-level regex never sees). A second row in the same file, `value=5.6729e+11, unit_str="$567,290 million"`, correctly resolves the same underlying magnitude for a nearby figure only because that sentence happens to repeat the word "million" explicitly. This is a separate-but-related failure mode from the decimal-truncation bug above (implicit table-scale context lost, rather than a mid-number split) and confirms the extractor's dollar values cannot be trusted at face value without manual spot-checking — two mentions of what should be the same order-of-magnitude backlog differ by six orders of magnitude in this one cached file.

### Minor
- `VALUE_RE` (L63-68) requires a currency symbol/code to *immediately precede* the number (`(?:[\$€£]|CAD|USD|C\$|US\$)\s?(\d+...)`). A common phrasing like "backlog grew to 1.2 billion dollars" (unit word trailing, no leading symbol) will not match at all, silently yielding `value=None` for an otherwise well-formed reading. Reduces recall; not a magnitude-corruption risk like the bug above, just a missed extraction.
- This is a single-ticker/CLI research tool (`--ticker`/`--cik`, no batch/driver wrapper in scope), so the blast radius of any one run is one company's `edgar_mda_readings.csv`; still, the existing `edgar_mda_readings.csv` in the repo should be spot-checked for any backlog value that looks suspiciously small (a symptom of this exact truncation bug) since it may already contain corrupted rows from a prior run.

## edgar_to_yartseva.py

### Docstring promises a computation step that does not exist in the code — confirmed via schema diff against real output

The module docstring (L9-14) claims this script adds "The full set of yartseva-schema columns (rev_yoy, ebitda_yoy, rev_accel, inflection flags, etc.) computed from EDGAR's multi-period XBRL data via additional company-facts queries." `build_yartseva_row` (L131-306) contains **no** such computation anywhere — it only maps single-period TTM/FY snapshot fields (`revenue_ttm`, `ebitda_ttm`, margins, valuation ratios) from `edgar_universe_facts.csv`; there is no YoY delta, no acceleration, no inflection-flag logic, and no "additional company-facts queries" (the only cache touched is the already-extracted flat CSV). Verified against the live output: `sorted(pd.read_csv('us_edgar_yartseva.csv').columns)` contains none of `rev_yoy/ebitda_yoy/rev_accel/*_inflection*`, while `uk_yartseva.csv` (a yfinance-derived sibling file this script's docstring says its output should interoperate with) has 22 such columns (`rev_yoy, rev_accel, rev_inflection, ebitda_yoy, ebitda_accel, ebitda_inflection, cfo_yoy, cfo_accel, cfo_inflection, fcf_yoy, fcf_accel, fcf_inflection, inflection_flag, inflection_score, roce_inflection, ...`). Since the docstring (L6-7) explicitly states "the EDGAR row supersedes the yfinance row when `build_asymmetry_global.sh` aggregates everything," every US ticker whose EDGAR row wins that supersession loses all growth/acceleration/inflection signal entirely (NaN) for a whole family of columns that other book-builders and archetype/rank scripts (already audited elsewhere in this repo) key off of — this is a real, silent coverage regression for the "higher-quality, audited" data source specifically, the opposite of what the file's stated purpose promises. Whether downstream consumers `fillna(0)` (silently treating "no data" as "no growth," penalizing real growers) or `.dropna()`-gate on these fields (silently excluding EDGAR-superseded US names from any inflection/acceleration-based screen) depends on the consuming script, but either way it's a real, unflagged asymmetry between EDGAR-sourced and yfinance-sourced rows in the same downstream pipeline.

### Ticker-symbol cross-contamination in `fetch_prices_cached()` — confirmed collision with real data

`fetch_prices_cached()` (L35-76) globs **every** `*_yartseva.csv` in the repo (L47) — not just US-relevant ones — concatenates them, and dedups purely on the bare `symbol` string (L68-71), with no `src`/country/currency disambiguation. Any ticker symbol that is reused across two unrelated listings in two different countries' cached files will have its price/market-cap/sector silently pulled from whichever file's row wins the "has market_cap, has sector" sort tiebreak (L68-69) — which need not be the US listing at all. Verified concretely: `edgar_universe_facts.csv` has a US entity `ATS Corp /ATS` (symbol `ATS`), and `at_gap_yartseva.csv` — one of the smaller, more narrowly-scoped country gap-fill files — separately has a row for symbol `ATS` at price $28.03 / market cap $2.72B (likely the unrelated Canadian ATS Corporation, NYSE: ATS, a $2.7B automation-tooling company, not the tiny SEC filer EDGAR resolved `ATS` to). Broader overlap counts against the EDGAR universe: `rest_expansion_yartseva.csv` (5,794 overlapping symbols), `fdb_expansion_yartseva.csv` (2,112), `otc_expansion_yartseva.csv` (499) — most of that volume is plausibly the *same* US company re-appearing across the pipeline's several global-expansion dumps (benign), but the `at_gap` case demonstrates the join has no guardrail against genuine collisions, and with 100+ heterogeneous country/gap/expansion files feeding the same bare-symbol pool, more such collisions are likely present un-audited. Recommend joining on `(symbol, src=="US")` or a CIK/exchange-qualified key rather than bare ticker string.

### Minor
- `if r.get("cfo_ttm") and r.get("ebitda_ttm") and r["ebitda_ttm"] != 0:` (L226) and several similar guards throughout use Python truthiness (`and`) rather than `pd.notna()` — a legitimately-reported value of exactly `0` (e.g. `cfo_ttm == 0`) is treated as "missing" and the derived field (`cash_conversion`, `fcf_yield` via `r.get("fcf_ttm")` at L254, etc.) is silently skipped rather than computed as `0`. Low impact (exact-zero flow values are rare) but an inconsistent missing-vs-zero convention repeated throughout the file.
- `r["gross_margin"] = None` (L223) is set unconditionally — fine as documented ("not separately extracted from XBRL"), just noting this column will read 100% NaN in the output for every row, which is expected/intentional here but easy to mistake for a bug when scanning coverage stats.

## edgar_universe_extract.py + edgar_roic_roiic.py

These two share the `edgar_cache/CIK########.json` dependency: `edgar_universe_extract.py` populates it, `edgar_roic_roiic.py` (CACHE_DIR = `Path("edgar_cache")`, L52) reads it read-only.

### Durability gap — `edgar_cache/` is gitignored, currently EMPTY on disk, and has no persistence script (unlike `edgar_segments_cache/`)

`.gitignore` line 8 ignores `edgar_cache/`, and `ls edgar_cache` at audit time returns "No such file or directory" — the directory does not exist at all right now, even though `edgar_roic_roiic.csv` on disk (7,972/10,433 rows with `n_years` populated) proves it existed and was fully harvested at some earlier point in this container's life. This is the exact "ephemeral cache lost when the container is reclaimed" failure mode that `persist_edgar_segments.py`'s docstring says already happened once for `edgar_segments_cache/` — except here there is **no equivalent `persist_edgar_*` split-gzip mechanism** for `edgar_cache/` or for `edgar_universe_facts.csv`'s underlying raw source. Re-running `edgar_roic_roiic.py` right now would silently produce a CSV of near-empty rows (every `process_one` call hits `if not cache_path.exists(): return {"symbol":..., "cik":...}` at L412-413) while still reporting success (`wrote edgar_roic_roiic.csv: N rows`), overwriting the good, populated `edgar_roic_roiic.csv` that currently exists with a gutted one — another instance of "state that reports success while quietly losing all its data." Recommend either persisting `edgar_cache/` the same way `edgar_segments_cache/` now is, or having `edgar_roic_roiic.py` refuse to overwrite `--out` when coverage regresses sharply vs. the prior file.

### edgar_universe_extract.py — error handling is materially better than edgar_full_harvest.py's (contrast, verified clean)

`fetch_companyfacts` (L252-279) correctly distinguishes a genuine 404 (cached permanently as `{}`, L264-267 — appropriate since a 404 from SEC means "no such filer," a stable fact) from a transient failure (429 backoff-and-retry L268-270; `HTTPError`/`ConnectionError`/`Timeout` retried up to 3x with exponential backoff, L275-278) from an unrecoverable-this-run failure (returns `None`, L279, **without writing anything to the cache**). `task()`/`main()`'s `if data is None: return None` (L477-478) then simply omits that ticker from this run's output rather than fabricating a fake-success cache entry. This is the correct pattern the audit is checking for, and it is a good contrast to the swallow-and-mark-done bug found in `edgar_full_harvest.py`.

One residual gap: `r.json()` (L272) can raise `json.JSONDecodeError` on a malformed/truncated response body, which is **not** in the `except (requests.HTTPError, requests.ConnectionError, requests.Timeout)` tuple at L275 — it propagates uncaught out of `fetch_companyfacts`/`task()`, to be caught only by `main()`'s outer `except Exception as e: row = {"symbol":..., "error": ...}` (L487-488). No cache file is written in this path (the crash happens before the `cache_path.write_text(...)` call), so it is still safely retryable next run — just noting the exception travels further than the inner retry loop intends.

Also: `cache_path.write_text(json.dumps(data))` (L273) and the 404 cache-write (L266) are **not atomic** (no tmp+rename), unlike the pattern used elsewhere in this codebase (`edgar_full_harvest.py`'s `write_json_atomic`). A hard kill mid-write could leave a truncated JSON file; mitigated in practice because the read path (L256-259) catches `json.JSONDecodeError` and falls through to re-fetch — so a truncated cache file self-heals on the next run rather than poisoning state. Low severity given that mitigation, but worth aligning with the atomic-write convention used elsewhere.

### Sign/unit note — negative-invested-capital compounders are systematically excluded from ROIC/ROIIC/ROCE (both files)

Both `edgar_roic_roiic.py` (`df["roic"] = np.where(df["ic"] > 0, ..., np.nan)`, L176; same guard on `cash_roic`, L177) and `edgar_universe_extract.py` (`if invested and invested > 0 and opi is not None: row["roce"] = opi / invested`, L393-395) require invested capital to be strictly positive. Well-known aggressive-buyback compounders with negative book equity (e.g. companies that lever up and repurchase past the point of positive equity) will have `ic <= 0` and get **no** ROIC/ROIIC/ROCE at all — not a wrong-signed number, but a silent `NaN`/missing field for exactly the subset of extreme capital-return machines this "Multibagger Reinvestment Engine" methodology is nominally trying to reward. Given the file's own emphasis on "durable reinvestment quality," this blind spot is worth a deliberate methodology call rather than an implicit `np.where` guard — flagging as a real methodology gap, not a crash risk.

### Minor
- `edgar_universe_extract.py` `base_delay = max(0.10, args.workers/10.0 - 0.05)` (L472): with the default `--workers 8`, this yields `0.75`s, and for a fast network round-trip the steady-state aggregate request rate approaches `workers/base_delay ≈ 10.7 req/s`, mildly *above* the "10 req/sec ceiling" the comment (L471) claims to stay under. In practice the 429 retry (L268-270) absorbs any resulting throttling, so this is cosmetic, not a correctness bug.
- `edgar_roic_roiic.py`'s `df["equity"].fillna(0)` / `df["total_debt"]` fillna(0) (L169-170) treats a *missing* equity/debt observation the same as a *reported-zero* one when computing `ic` — for the (rare, mostly early-filer) case where equity truly wasn't reported that year, this silently biases invested capital downward rather than leaving the year's ROIC as NaN via a missing-data path. Low frequency in practice (equity is a near-universal 10-K line item) but worth noting as an implicit "missing == zero" assumption.

## edgar_full_harvest.py

Live processes confirmed running during audit (4 shards, `--stage xbrl --shard {0,1,2,3} --num-shards 4 --workers 1`, pid 1702-1705). Snapshots of the 4 shard state JSONs and `edgar_segments_cache/` were copied to the scratchpad before probing.

### CRITICAL — internal `except` blocks swallow fetch failures into a payload that is then cached AND marked permanently done (data loss disguised as success)

All three harvesters (`harvest_xbrl_dimensional` L170-186, `harvest_form4` L296-300, `harvest_proxy` L361-365) catch their own top-level lookup/list exceptions and **return a dict** like `{"cik":cik, "symbol":sym, "error": "..."}` instead of raising or returning `None`.

The corresponding `stage_*_one` drivers only special-case `payload is None`:
```
stage_xbrl_one   L279-284: payload = harvest_xbrl_dimensional(...)
                 if payload is not None: write_json_atomic(cache_path, payload)
                 state[...]["status"] = "xbrl_done"      # <-- always runs, even for error payloads
```
Same pattern in `stage_form4_one` (L344-348) and `stage_proxy_one` (L392-396).

Effect: a transient SEC rate-limit (429), a network blip, a symbol lookup failure, or any edgartools exception on `Company(symbol)` / `get_filings(...)` is written to `edgar_segments_cache/CIK##########.json` (or the insider/proxy caches) as a tiny `{"error": ...}` stub, and the CIK is marked `xbrl_done`/`form4_done`/`proxy_done` — indistinguishable in state from genuine success. On any later run, `stage_xbrl_one`'s `cache_path.exists()` check (L276-278) short-circuits to `"cached"` before even calling the harvester again, so **the CIK can never be retried** — the failure is permanent and silent. This directly matches the audit's "state files that can mark work done when it failed" pattern.

Corroborating evidence: `harvest_shard{0..3}.log` show `err=0` across ~900-3500 processed CIKs each, for a run hitting SEC's API thousands of times with `--workers 1` per shard × 4 concurrent shard processes. Given the volume, genuine zero transient failures is implausible — far more likely such failures are occurring and being funneled into this silent "done" path rather than incrementing the `err` counter (which only increments when an *uncaught* exception escapes `stage_fn`, L432-433/440-441 in `run_stage`). No `edgar_segments_cache/*.json` file currently contains an `"error"` key (checked all 2749 files), so no confirmed loss yet in this session's window, but the code path is real and will trigger under any sustained rate-limiting or network hiccup — the fix is to only mark `*_done` when the payload lacks a top-level `"error"` key (or route errors to a distinct `*_error`/retryable status, which the `except Exception` wrapper around the *call itself* already does correctly for exceptions that do propagate — L285-288, L350-353, L398-401).

### Doc/implementation mismatch — no rate limiting exists despite the docstring's claims

Module docstring (L22-23): "**Polite rate limiting**: SEC's 10 req/sec ceiling honoured via a shared semaphore. Backoff on 429." `grep -n "semaphore\|429\|backoff" edgar_full_harvest.py` finds **nothing** — there is no semaphore, no 429 detection, no backoff anywhere in the file. The only throttling in the whole script is `time.sleep(0.1)`/`time.sleep(0.15)` inside the form4/proxy per-transaction loops (L321, L379) — the xbrl stage (the one currently running) has zero throttling. This makes the silent-swallow bug above materially more likely to trigger at scale, since nothing protects the 4 concurrent shard processes from tripping SEC's rate limiter.

### SIGTERM/SIGINT handler does not actually stop the run promptly (contradicts "survives kill cleanly" design goal)

`run_stage` (L427-428) submits **all** rows to the `ThreadPoolExecutor` up front: `futures = {ex.submit(stage_fn, r, state): r for r in rows}` — for a 2,500-CIK shard that's 2,500 queued tasks against `workers=1`. The signal handler (L103-114) does `save_state(state); sys.exit(0)`. `sys.exit` raises `SystemExit`, which propagates out of the `for fut in as_completed(futures):` loop and through the `with ThreadPoolExecutor(...) as ex:` block — but `ThreadPoolExecutor.__exit__` calls `self.shutdown(wait=True)` with no `cancel_futures=True`, so it does **not** cancel the ~2,500 queued-but-not-yet-started tasks; it drains the entire queue before the process actually exits. So sending SIGTERM does checkpoint state immediately (good) but the process keeps running for the full remaining ETA (tens of minutes per the logs) rather than exiting — defeating the stated purpose of a "clean, prompt" signal-triggered exit. A supervisor that sends SIGTERM then SIGKILL after a short grace period will still lose all progress made after the single checkpoint taken at signal time, because the intervening completed-but-not-yet-checkpointed work (up to `CHECKPOINT_EVERY=50` more CIKs) is discarded by the hard kill.

### Signal handler performs file I/O from within a signal handler (async-signal-safety hazard)

`_handle` (L106-112) calls `save_state(state)` — a `json.dump` + `os.replace` — directly inside a signal handler installed via `signal.signal`. If SIGTERM arrives while the main thread is itself mid-way through a periodic `save_state(state)` call (L445 in `run_stage`, at every 50th checkpoint) — e.g. between `open(tmp, "w")` and `os.replace` — CPython signal handlers run on the main thread between bytecode instructions, so this is not thread-unsafe in the classic sense, but reentrant `open()`/`json.dump()` calls into the *same* `.tmp` path while the outer call has that path open for writing can still interleave (the outer call's file handle keeps writing into the truncated file after the handler's independent `open(...,"w")` reopened/truncated the same inode, since both open the same path). Low probability given the narrow window, but combined with the executor-drain bug above, a signal delivered mid-checkpoint is a plausible double-write race on `edgar_full_state.shard*.json.tmp`.

### Minor / non-fatal observations
- `load_universe()` (L126-143) writes `sec_company_tickers.json` via a plain `cache.write_text(...)` (L138) — **not** atomic (no tmp+rename), unlike every other write path in this file. If two shard processes start simultaneously on a cold cache, both fetch and both write, and any third reader could observe a truncated file mid-write. Currently moot since the cache file already exists, but inconsistent with the file's own "atomic writes" design principle.
- `load_universe()` builds one row per **ticker**, not per CIK, then only `drop_duplicates("symbol")` (L143) — a CIK with multiple listed tickers (dual share classes) is processed multiple times (redundant work, resolved harmlessly by the cache-exists check, not a correctness bug).
- `fut.result(timeout=120)` (L431) on a `ThreadPoolExecutor(max_workers=1)`: a timeout does **not** cancel the underlying thread (Python futures can't be cancelled once running) — the task keeps executing consuming the sole worker slot, while the code logs a fabricated `cik=-1` error entry unrelated to the actual stuck CIK. Harmless to data integrity (the real CIK's status is simply never updated, so it's retried next run) but makes the error logging misleading.
- Shard determinism itself is correct: `universe["cik"].astype(int) % args.num_shards == args.shard` (L499) is a clean, deterministic, disjoint partition, and the shared `edgar_segments_cache/` directory is written by CIK-keyed filenames, so no two shards ever target the same output file — no actual cross-shard race on the cache files themselves.
